# Phase 9 operational metadata retention — review draft

The product specification proposes 30 days for operational metadata, while private text and session records remain until owner deletion or a published account policy. This is a **draft boundary**, not a published customer promise or permission to delete safety, financial, or evidentiary records. Supabase remains local-only.

The 2026-09-28 [read-only local inventory](../evidence/phase9/metadata-retention-inventory.json) counted six candidate tables by total rows and rows older than 30 days. All six had **zero** rows older than 30 days, so no purge was needed or attempted. The inventory intentionally emitted no household IDs, notes, model prompts, audio or credentials. It does not cover every table with a `created_at` column, backups, Supabase Auth internals, or provider-side retention.

Before a purge exists, define each table's purpose and exception. `public.audit_events` may be needed to explain a safety restriction; `public.outbox_events` has dependent `public.deliveries` and may contain unresolved work; `private.idempotency` and `private.household_creations` protect retries; `private.provider_calls` supports budget and cost reconciliation; `private.deletion_requests` is a cleanup receipt and is referenced by `private.demo_deletion_codes` until that credential is removed. A single age-based `DELETE` across these tables would be unsafe. Existing whole-household primary deletion remains the separate, explicit disabled-first workflow.

`private.record_view_sessions` has a separate, already implemented 30-minute access window. An expired row is also a **denial marker**: deleting it while the original auth session is still fresh could let that same session insert a new row. The one-shot local tool `scripts/run-phase9-view-session-prune.ts` therefore previews expired rows but permits removal only after their original auth session is absent or no longer within the 30-minute fresh-auth window. Its default command is a read-only aggregate preview; `--grant-id <exact-uuid>` narrows that preview. Mutation requires `--apply --grant-id <exact-uuid> --limit <1-100>` and rechecks row expiry and session freshness inside the delete statement. It emits only counts, never private content or IDs, and refuses non-local database targets. This is an exact-grant local maintenance operation, not a global scheduler or the proposed 30-day metadata policy.

The next policy decision is a table-by-table schedule with a start event, minimum and maximum retention, unresolved-job exceptions, audit/incident holds, backup expiry, and customer-facing wording. Only after that review should a local dry-run selector and exact-row tests be built. Do not retroactively purge older unconsented fictional fixtures or claim continuous operation from a one-shot command.

## October 21 decision worksheet — still unapproved

The remaining work is a policy and correctness decision, not an age-based purge. No new purge or scheduler is implemented by this worksheet. Treat the following as questions for the owner/privacy reviewer and implementation constraints; the proposed 30 days is not a legal conclusion or a selected retention promise.

| Record class | Start event to decide | Required exceptions and correctness boundary | Decision needed before implementation |
|---|---|---|---|
| `audit_events` | Event creation, incident closure or a defined final disposition | Safety restriction explanations and unresolved incidents may need the relevant event chain; deleting older context can make a newer event misleading | Named purpose, minimum/maximum period, incident hold/release and authorization to remove each field |
| `outbox_events` and dependent `deliveries` | Terminal delivery/cancellation, not enqueue time | Pending/processing/retry/dead-letter work is unresolved; retain parent/child linkage and enough outcome to prevent duplicate dispatch | Terminal-state definition, dependency order, failed-job exception and monitoring/rollback owner |
| `private.idempotency` and `private.household_creations` | End of an explicitly enforced retry window, not merely first request age | Removing a receipt can let an old key repeat a consequential action. A server-enforced old-request refusal or retained minimal tombstone must exist first | Maximum accepted retry age, behavior after that age, minimal receipt fields and duplicate-work regression criteria |
| `private.provider_calls` | Reconciliation/dispute closure and budget-window completion | In-flight/unknown outcomes and unreconciled units must not disappear. Usage units do not establish a dollar bill or AWS-side retention | Purpose, reconciliation exception, required fields, period and provider-side evidence owner |
| `private.deletion_requests` and `private.demo_deletion_codes` | Verified cleanup completion plus expiry of dependent deletion-only credentials | Pending/failed cleanup remains disabled and retryable; preserve proof/credential dependencies until safely resolved; never reinstate access while pruning | Minimal completion receipt, failed-job period/escalation, dependency expiry and backup wording |
| `private.record_view_sessions` | Expired view window plus original login session no longer fresh | Expired row remains a denial marker while the original session is fresh. Existing exact-grant prune tool enforces this independently | Confirm this narrow maintenance purpose and its operating cadence; do not replace it with general age deletion |
| Raw transcripts/audio and private household/session content | Separate explicit record/provider policy | Unsaved transcript memory expiry, server transport behavior, saved records and provider storage are different scopes | Separate policy wording and account-configuration evidence; no unsupported zero-retention claim |
| Local backup files / restored copies | Backup creation and verified disposal | Dumps can contain Auth/private records and outlive primary deletion. A database restore alone does not configure backup expiry or revoke downloaded copies | Access/encryption/custodian, approved lifetime, inventory, disposal verification, restore access and customer-facing limits |

For each row, leave these fields blank until a real decision: reviewer/authority; version/date; purpose; start event; minimum/maximum; unresolved/incident hold; fields retained; deletion authority; backup exception; failure handling; public wording. Avoid collecting reviewer personal details in public artifacts.

After review, the implementation sequence is: encode the approved policy version; add a read-only exact-row selector; test unresolved/dependent/duplicate/retry/incident cases; review an aggregate preview; only then consider narrowly scoped application. Keep older unconsented demos excluded. Whole-household primary deletion and existing exact-grant maintenance retain their explicit boundaries. No standing automation, hosted service or actual policy approval is created here.
