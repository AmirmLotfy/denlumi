# Phase 9 fictional demo retention — local operating boundary

New browser-created fictional samples disclose this local rule before creation and require an unchecked, labeled acknowledgment choice: access ends after 24 hours; primary household records become eligible for cleanup seven days after creation. Cleanup happens only when the one-shot local worker runs, so it may be delayed. The app does not promise historical backup erasure or recall a recipient's downloaded copy. No real animal-handling information should be entered. This is an R0 local sample rule, not a published customer privacy policy or a legal retention determination.

The local migration `20260923010307_phase9_demo_retention_consent.sql` added an acknowledgment timestamp and purge timestamp. Older samples have neither value and **are never selected** by the worker. Live households, unconsented demos, demos younger than seven days, and unexpired demos are excluded. The cleanup uses the same disabled-first, schema-checked primary deletion transaction as owner deletion; it leaves the owner identity and historical backups outside its scope. A schema change fails visibly, leaves access disabled and allows an exact-ID retry after correction.

A focused local Supabase Data API test also tried to forge retention consent on an unconsented household and verified that the stored acknowledgment remained null. Only server-side sample creation records the acknowledgment.

Run `npx tsx --env-file=.env.local scripts/run-phase9-demo-cleanup.ts` for a read-only aggregate preview. A local operator may run `npx tsx --env-file=.env.local scripts/run-phase9-demo-cleanup.ts --apply --household-id <exact-uuid>` for **one** previously verified, consented, due fictional household, or `npx tsx --env-file=.env.local scripts/run-phase9-demo-cleanup.ts --apply --limit 20` for at most 20 due, consented fictional households. The batch selects IDs read-only, then processes them serially; each row is rechecked under a lock before access is disabled. No scheduler is configured. Do not run this against existing unconsented fixtures. The script refuses non-local database targets and emits status/counts rather than private content or IDs.

For an explicit local batch scope, append `--household-ids <uuid-1,uuid-2,...>` to `--apply --limit <1-20>`. The selector then considers **only** those 1–20 unique IDs, still requires each row to be fictional, consented, expired and seven-day-old, and still rechecks each selected row under lock before deletion. It refuses malformed or duplicate IDs and never prints them. Omitting this option retains the earlier all-due selector; it must be used only after checking the dry run and the local operating context.

The dry run now separately counts ready, failed, pending, stalled processing (older than two minutes) and active processing consented-demo jobs. A failed exact-ID apply exits nonzero and reports only a status and error code. After correcting the cause, an operator can retry that **same exact ID**; the worker checks eligibility and request identity again. Pending and stalled jobs can be retried through the bounded batch, but a zero-count dry run does not prove a scheduler or monitoring service is running.

For **newly acknowledged** fictional samples, the server now issues a separate high-entropy deletion code once at creation. Only its SHA-256 digest is stored in `private.demo_deletion_codes`; the browser does not persist the code in local or session storage. The person must save it privately while it is visible. After the 24-hour access expiry, and before the seven-day cleanup date, possession of the exact code plus typed `DELETE` and a checkbox can request primary cleanup for that one fictional household even if its anonymous browser session has been lost. This route never reopens plans, history, guidance or account access. Anyone who obtains the code can delete that exact sample, so it is a deletion credential, not an account-recovery credential. A wrong, changed, unexpired, expired-code or already-used code is refused. A failed cleanup leaves access disabled; the same code can retry the existing request while it remains valid. Older unconsented samples have no code and are not retroactively enrolled.
